# RetailCo ETL – guide for AI assistants

Read this file first. It explains what the project does, the rules to follow, and how to check that a change works.

## 1. What the project does

A nightly sales CSV is loaded into a SQL Server staging database, cleaned, and loaded **incrementally** into a star-schema data warehouse that keeps history.

```
data/<env>/inbox/*.csv
   -> python main.py run                        (file already loaded? fileHash in etl.runLog -> skip file)
   -> RETAIL_STG.stg.salesRaw                   (file as received, all text, loadedAt)
   -> RETAIL_STG.stg.salesClean                 (view: cleaning rules + lineHash per line)
   -> EXEC RETAIL_DWH.etl.loadWarehouse @runId  (loads only this file)
        dim.calendar   add missing days
        dim.product    SCD type 2 (stockCode; tracks description, productType)
        dim.customer   SCD type 2 (customerId; tracks country), key 0 = guest
        fact.sales     soft-delete lines missing from re-sent invoices,
                       insert new lines, skip lines whose lineHash is already active
        etl.dataQuality + etl.runLog (inserted / skipped / deleted counts)
   -> file moved to data/<env>/archive (or data/<env>/error on failure)
```

- **Nothing is truncated or physically deleted.** History is kept with SCD2 versions and soft deletes (`isDeleted`, `deletedAt`, `deletedRunId`).
- **Source data:** UCI Online Retail, dataset 352 (CC BY 4.0), 541,909 rows, 1 Dec 2010 – 9 Dec 2011.
- **Other documents:**
  - stakeholder report: `docs/retail_data_platform_report.docx`
  - all documentation (process, SCD2, cleaning rules, deletes advice, how to run): `readme.md`
  - the original brief: `docs/brief/`

## 3. Division of work – do not mix these up

- **Python only moves files and data:** read the CSV, insert into `stg.salesRaw`, call the procedure, move the file.
- **All business and cleaning logic lives in SQL:** cleaning in the view `stg.salesClean`, modelling in `etl.loadWarehouse`.
- Never put cleaning rules in Python. Never add a second cleaning location.

## 4. Naming convention (strict)

| Item | Rule | Example |
|---|---|---|
| Files and folders | lower case | `sql/2_staging.sql`, `readme.md` |
| Databases | `RETAIL_` + layer, upper case | `RETAIL_STG`, `RETAIL_DWH` |
| Schemas | role, lower case | `stg`, `dim`, `fact`, `etl` |
| Tables, views, procedures, columns | camelCase | `stg.salesRaw`, `etl.loadWarehouse`, `invoiceNo` |
| SQL references | always three-part `DATABASE.schema.object` | `RETAIL_DWH.fact.sales` |
| Keys | end with `Key` | `productKey` |
| Money | end with `Amount` | `netAmount` |
| Counts | end with `Count` | `insertedRowCount` |
| Flags | start with `is` | `isDeleted`, `isCurrent` |
| Timestamps | end with `At` | `loadedAt`, `createdAt`, `updatedAt`, `deletedAt` |
| SCD2 columns | `validFrom`, `validTo` (9999-12-31 = open), `isCurrent` | `dim.product` |
| Constraints / indexes | `pk`, `df`, `ix`, `ux` + name | `pkSales`, `dfSalesLoadedAt`, `uxSalesLineHash` |
| Python | camelCase variables/functions, PascalCase classes, UPPER_CASE constants | `processFile`, `Settings`, `SQL_FOLDER` |

- The same field keeps the same name in every layer (`invoiceNo` in salesRaw, salesClean and fact.sales).
- Use full, readable names. No abbreviations like `cfg`, `con`, `rn`, `tmp`.
- **Reserved words – never use as column names:** `lineNo` → use `lineNumber`; `rowCount` → use `recordCount`. Check any new column name against the T-SQL reserved keyword list.
- SQL Server does not allow a database prefix on `CREATE SCHEMA / VIEW / PROCEDURE`. Those scripts start with `USE RETAIL_xxx; GO` and use a two-part name for the object being created; every other reference stays three-part.

## 5. Rules for changes

1. **Keep it simple.** The owner explicitly prefers fewer files, fewer tables and plain code. Do not add frameworks, layers, seed files or extra tables unless asked.
2. **Never truncate or hard-delete warehouse data.** Facts are insert-only; removals are soft deletes; dimension changes are new SCD2 versions.
3. **SQL scripts must stay re-runnable** (`IF OBJECT_ID(...) IS NULL CREATE TABLE`, `CREATE OR ALTER VIEW/PROCEDURE`). `python main.py setup` must succeed when run twice.
4. **`etl.loadWarehouse` must stay one transaction** with `TRY/CATCH`, must process only its `@runId`, must be safe to re-run (re-running skips everything), and must always update `etl.runLog`.
5. **All queries on `fact.sales` must filter `isDeleted = 0`.** To show current names or countries, join to the dimension row with `isCurrent = 1`. To show history, use the key stored in `fact.sales`.
6. **New tracked attribute on a dimension:** add it to the table, to the `#file...` temp table, to the "changed" comparison, and to both INSERTs in the SCD2 step.
7. **Changing a table's columns:** `IF ... IS NULL` will not alter an existing table. In dev, drop and recreate the databases (section 7), then reload. For prod, write an explicit `ALTER TABLE` script and tell the owner.
8. **Never edit rows in `stg.salesRaw`.** The only allowed delete is removing a failed run (`WHERE runId = ...`), which `pipeline.py` already does.
9. **New data-quality check:** add the count to the `totals` subquery and a row to the `VALUES` list in step 7 of `etl.loadWarehouse`.
10. **New business question:** add `sql/queries/<n>_<name>.sql` with first line `-- Q<n>. <title>`. Query only RETAIL_DWH tables. `python main.py report` picks it up automatically.
11. **New environment:** copy `.config/example.env` to `.config/<name>.env`. Database names are the same in every environment; only the server and folders change.
12. **Secrets:** never put passwords in code or commit `.env` files (only `example.env` is tracked). Default login is Windows authentication.
13. **Docs:** all project documentation is in one file, `readme.md` (with the Mermaid diagrams). If behaviour or names change, update `readme.md` and this file. Do not create other readme or design files.

## 5b. Dashboard rules

- Run with `streamlit run dashboard/streamlit_app.py`. It reads RETAIL_DWH through `etl/settings.py` (same `.config` environment).
- All SQL lives in `dashboard/data.py` as cached (`st.cache_data`) queries; pages only filter and chart the cached data.
- Every chart's insight note must be **calculated from the filtered data** (no hard-coded claims), because users change the filters.
- Queries on `fact.sales` filter `isDeleted = 0`; customer value is shown **net of cancellations**.
- Charts use Altair; no `use_container_width` (deprecated). Test every page headlessly with `streamlit.testing.v1.AppTest`, with and without a country filter.

## 6. Environment facts

- **Server:** SQL Server 2025 Developer on `GHOST`, Windows authentication, ODBC Driver 18 for SQL Server. Uses `GENERATE_SERIES` and `GREATEST`, so SQL Server 2022 or later is required.
- **Python:** 3.14; dependencies are in `requirements.txt` (`pyodbc`, `python-dotenv`).
- **Collation:** the default server collation is case-insensitive. Lines are identified with `HASHBYTES('SHA2_256', ...)` over the cleaned values (`lineHash`) so comparisons are exact.
- **VS Code formatter:** the owner's SQL formatter is not T-SQL aware and may reformat `.sql` files when they are open. If a SQL file suddenly looks different, check it still runs with `python main.py setup`. It previously broke `N'text'` into `N 'text'`.
- **`RetailDB`:** another database on the server. It is not part of this project – do not touch it.

## 7. How to test a change (always do this)

```powershell
# clean dev rebuild (dev only - this deletes the dev databases)
sqlcmd -S GHOST -E -C -Q "ALTER DATABASE RETAIL_STG SET SINGLE_USER WITH ROLLBACK IMMEDIATE; DROP DATABASE RETAIL_STG; ALTER DATABASE RETAIL_DWH SET SINGLE_USER WITH ROLLBACK IMMEDIATE; DROP DATABASE RETAIL_DWH;"
python main.py setup
# put the source CSV in data/dev/inbox (python main.py extract, or move it back from data/dev/archive)
python main.py run
python main.py report
```

Scenario tests (all passed when the design was built):

| Case | Expected |
|---|---|
| `python main.py run` with an empty inbox | prints "inbox is empty" |
| exactly the same file again | "already loaded before, skipped", moved to archive |
| file with all lines of invoices 536365 + 536366 again | 0 new, 9 already loaded, 0 soft-deleted |
| invoice 536365 with one quantity changed and one line removed | 1 new, 5 already loaded, 2 soft-deleted |
| new invoice: customer 17850 in France, product 85123A renamed | new SCD2 versions; old invoice 536365 still points to the old versions |

| file missing columns | moved to `error/`, `etl.runLog.status = 'failed'`, exit code 1 |

After scenario tests, return to a clean state with the full rebuild above. Test rows cannot be removed simply, because the warehouse never deletes.

## 8. Known limits (not bugs)

- A file is assumed to contain complete invoices. A partial invoice would soft-delete that invoice's other lines.
- An invoice deleted at the source and never sent again cannot be detected from daily files. See `readme.md` section 8 for the recommended options; cancellation invoices are the preferred way.
- SCD2 detects at most one change per product or customer per file, effective from the first date it appears in that file.
- The data has no product category, so category questions from the brief are not answered.
- About 25% of lines have no customer number; they are kept as the guest customer (`customerKey = 0`).
- December 2011 contains only 1–9 Dec.

## 9. Reporting figures

Figures in the stakeholder report come from RETAIL_DWH queries. If the data or rules change, re-run the queries and update `docs/retail_data_platform_report.docx`. The numbers in it are not linked to the database.
